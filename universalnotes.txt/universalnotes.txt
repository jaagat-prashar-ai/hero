- The -0.4 value has two separate origins layered on top of each other — worth separating clearly:

1. The number itself is inherited, not derived. reasoning_threshold = -0.4 is copied verbatim from the vendored upstream NVlabs recipe (third_party/alpamayo-recipes/.../aggregated_reward_with_reasoning.py:109), which was built for a completely different grader — LingoJudge, a local text-similarity classifier outputting a raw quality score in [0,1], where reward = raw - 1.0 and -0.4 meant "pass if raw ≥ 0.6." Commit 77802f3 (2026-07-21, "add aggregated reward with LLM-judge reasoning component") explicitly ported this into the new gpt-4o-judge reward file with the note: "Mixing formula, thresholds, and return contract are preserved verbatim so the validated GRPO behavior carries over." So -0.4 wasn't chosen for the LLM judge — it was carried over unchanged when the judge was swapped in.

2. Mapping the new judge onto that inherited scale. The gpt-4o judge outputs an integer 0-10, not a [0,1] float, so normalize_score() (llm_judge.py:243) maps it: score/10 - 1.0. Under that mapping, -0.4 corresponds exactly to judge score > 6.

3. The only actual validation of "6" as a cut point: an offline calibration study — reasoning_matched_pairs.jsonl, 717 judged pairs across 120 scenes (commits fe87c81/63fa137, from the dpo_pairs/preference-pairs work) — where the judge scored "chosen" (real, good) vs. "corrupted" (perturbed, bad) reasoning traces. Result: chosen-trace median score 7, corrupted-trace median score 1. Since 6 sits just below the chosen median and well above the corrupted median, it was judged "a sensible acceptance bar" (comment in llm_judge.py:250).

The catch, already flagged in the code and still unresolved: that 717-pair calibration was run with the text-only judge prompt. The production path you're actually running (7bgtj3, scene-grounded — image + trajectory overlay) uses a different prompt variant, and the code comment itself (llm_judge.py:121-125) says the scene-grounded score distribution "may sit elsewhere" and to "watch the first canary run's histogram before trusting the threshold unchanged." Nobody has re-run the chosen-vs-corrupted calibration with the scene-grounded prompt — we only have the histogram I pulled from 7bgtj3 itself, which happens to be bimodal with nothing near the score-6 boundary, so at least the gate isn't splitting hairs on this particular run. But that's a property of this run's outputs, not a re-validation of 6 as the correct cut for the scene-grounded judge.

So: -0.4 is an inherited default, remapped by arithmetic, and loosely sanity-checked against a text-only calibration that predates the scene-grounded prompt actually in use. If you want a real answer on whether 6 is right for scene-grounded gpt-4o, the 717-pair chosen-vs-corrupted study would need to be redone with the scene-overlay prompt.

It doesn't get thrown away, and it doesn't just get one flat "you failed" value either. Two things can happen:

1. If the model didn't produce any usable reasoning text at all (empty output), it gets the worst possible score: flat -1.0.

2. If it did produce reasoning text but missed the bar — either the trajectory was too far off (ADE ≥ 3.0) or the reasoning score was ≤ -0.4 — it gets a graded failure score, somewhere between -1.0 and -0.5. Where exactly it lands depends on how close it came to passing on each of the two checks:

- How close was the trajectory error to the 3.0 cutoff? (barely over → more credit; way over → no credit)
- How close was the reasoning score to the -0.4 cutoff? (barely under → more credit; deeply negative → no credit)

Average those two "closeness" measures and that sets where in the -1.0-to-0.5 band it lands. Always strictly worse than any passing rollout (which starts around -0.2 and can go positive) — but not maximally punished if it was a near-miss.

Why bother grading a failure instead of just giving everyone -1? Because of how this training method (GRPO) uses reward: it doesn't train on the raw number, it compares each rollout to the average of the small group of attempts sampled for that same scene. If every single attempt in a group gets the exact same flat -1, there's zero difference between them — nothing to learn from, wasted judge calls. By grading "how close," even a group where everything technically failed still has some attempts that failed less badly than others, so there's still a gradient nudging the model toward the ones that came closer.

The five charts, in plain terms

Reward, mean — the single combined score (trajectory accuracy + comfort + reasoning bonus/penalty, all mixed together) averaged across each training step. Grey wiggly line = the real noisy value every step; blue line = a 15-step rolling average so you can see the trend through the noise. Here it just bounces around -0.2 with no upward or downward drift — the model isn't visibly "getting better" by this score yet.

Reasoning score — same idea, but isolating just the judge's reasoning component (scale -1 to 0). The dashed red line at -0.4 is the pass/fail cutoff. It sits around -0.25 on average, below the cutoff — which sounds bad, but isn't a contradiction with the 74% pass rate below: the passing rollouts score close to 0 (barely above the line), while the failing ones score very negative (-0.7 to -1.0), so the minority of failures drag the average down harder than the majority of near-perfect passes pull it up.

Trajectory L2 — how far the predicted path is from the real (ground-truth) path; smaller is better. Dashed red line at 3.0 is the cutoff. This is the one chart that shows a real, if modest, improvement — the smoothed trend drifts down from about 2.5 to about 2.2 over the run.

Gradient norm — how big each training update to the model's weights is, plotted on a log scale (because a few values spike into the 20s-30s). It starts small and calm, then gets bigger and spikier in the back half of the run. Nothing broke here, but it's a flag: if this run were extended or repeated, that rising instability is worth watching.

Judge score histogram — how many sampled rollouts got each possible score, 0 through 10. The real finding: bars only exist at 0, 2, 3, 8, 9, 10 — scores 1, 4, 5, 6, and 7 never showed up at all across ~1,200 samples. # Rollout / Training plots
    # For each prompt in a batch, the rollout worker (vLLM) samples n_generation=12 completions of that same prompt - that's the GRPO "group." 
    # Then those 12 completons get scored by the reward function (the LLM-judge, in this run) to get 12 reward values. 
    # "Train" = a separate step that happens after a group of rollouts exist. It takes the completed (prompt, completion, reward) tuples, computes each completion's advantage as reward minus the group's mean reward, and does the actual backward pass / optimizer step on the policy weights using that advantage. 
    # Rollout produces data: sample 12 completions per prompt, score them, push into a buffer. Runs on the vLLM rollout replica. 
    # Train consumes data: pull a batch of already-scored groups out of the buffer, compute GRPO loss, update weights. Runs on the policy replica.

    # assembly line with 5 steps: 
        1. Find what's worth flipping - select_targets() (line 173). A claim parser reads each trace and tags the meaningful parts: commitments ("nudge left") perceptions ("cones blocking the lane"), causes ("due to..."), and numbers ("15 m"). For each, it marks the exact character positions. Six flip types are defined (line 82): direction flips (left <-> right), maneuever swaps (stop<-> proceed), state flips (blocking<-> clear, red<->green), entity swaps (pedestrian<-> cyclist), cause substitutions, and number corruptions. A scene only gets the types it has material for - on this corpus that averages ~4 per scene (477 jobs / 120 scenes).

        2. Ask Claude to make the edit - generate_perturbation_v2() (line 270). One API call per scene (scene, flip type). The system prompt (line 99) gives strict rules: change only the marked span, keep word count within +- 2, add no hedging words, reuse old vocabulary the corpus already uses. Those style rules exist because v1 of this tool failed exactly there - its edits had a detectable "written differently" smell.

        3. Trust nothing, verify mechanically - validate_perturbation() (line 229). Plain Python checks the model actually obeyed: is every character outside the edited span byte-identical? Is the word count within +- 2? Is it a real change, not a paraphrase? Violations get one fresh retry, then the job is skipped rather than letting a bad sample through. 

        4. The fingerprint gate - fingerprint_check() (line 416). After the batch is done, this replays the exact attack that killed v1: embed all real and fake texts, and try to classify real-vs-fake from text alone, with no scene or trajectory information. 
            # If that classifier beats 60% accuracy, the fakes have a giveaway and the corpus is rejected (v1 scored 95.8% - completely broken). Only a passing corpus is safe to train on, because otherwise the contrastive loss would learn to spot the giveaway instead of checking the trajectory.

The cross-cutting diagnosis (all six lenses converged on this)

Your current symmetric InfoNCE recipe under-delivers on consistency — as opposed to retrieval accuracy — for three structural reasons:

1. It's discriminative and information-thin. Winning K-way retrieval needs only ~log₂(K) bits of any fingerprint — template surface slots, speed numbers, prompt length — and those bits live in the throwaway text_proj/traj_proj heads that are discarded at inference. Nothing forces them to be causal semantics, and the same-frame group design even removes any pressure for the text embedding to read the image.
2. It's disconnected from the pathways that matter. The trajectory side is detached (driving.py:308), so all alignment gradient flows into text-side side-heads — the action computation is never required to read the reasoning. And the loss only ever sees teacher-forced GT text and GT trajectories, never the model's own generated commentary or own predicted waypoints. The deployment distribution where consistency must hold is literally untrained.
3. Almost every naive fix has a shortcut channel — steganographic waypoint dithering, positional scene caches through reasoning-token residual streams, template fingerprints, probe gaming. Ideas survived critique only when the shortcut is closed by construction, not monitored.

The frontier, per the synthesis: move consistency pressure onto the model's own likelihoods and own outputs, use interventional supervision with directional targets (already mineable from data on disk), and do measurement before mechanism — you have never actually measured whether baseline commentary is causally inert, and that number gates everything else.

Four independent critiques converged on "measure first." It piggybacks free on the full-data K-sweep's S3 checkpoints, and it's standalone publishable (Lanham faithfulness tests transplanted to continuous actions). Pre-registered decision rule: if sibling-CoC substitution moves ADE <5% and spread ≈ 0, baseline reasoning is decorative and the enforced-channel ideas get priority; if interventions already move actions, the loss-shaping ideas below become the frontier.

2. Grouped Inverse-Cycle (highest-scoring training idea, 4/4/4). A second trunk pass per dreamer batch: encode the model's predicted waypoints via the existing wp_encoder, drop all vision tokens, teacher-force each of the K sibling instructions, and apply a within-group softmax ranking loss over the K CEs — the true instruction must be the most likely explanation of the model's own trajectory. This exploits the one asset token-action VLAs don't have: exact gradients through a continuous regressed action into language CE, no REINFORCE. The two known kill-shots are closed by construction: within-group ranking (not absolute CE) kills the scene-token-smuggling gradient, and the vision-free pass keeps sequences short. ~150 lines in driving.py/utils.py, two arms (detach vs no-detach), with a steganography tripwire: if ranking accuracy collapses under 0.3 m Gaussian noise on eval waypoints, the model is dithering waypoints to encode the instruction — kill the undetached arm.

3. Minimal-Intervention Corpus (zero-cost data, highest novelty in the data lens). Because commentary/instructions are template-generated from privileged CARLA state, single-clause flips are exact and rule-based — no paid API. Emit K=2 groups where one causal clause is flipped (target = the matching dreamer sibling's GT trajectory) or deleted (target = original waypoints), with the intervention operator randomized and one operator held out of training purely for eval. Gradient lands exactly on the tokens that should explain the action. Metric: clause-flip action-sensitivity ratio vs a paraphrase control, ≥1.5× baseline or kill.         # Training only ever pushes in one direction: text goes in, a trajectory comes out. Nothing ever checks whether the trajectory the model produced actually reflects the instruction; the model is free to produce reasoning and driving that are only loosely related. 

    The idea adds a second check within the same training step, using the dreamer groups you already have (one camera frame, K different instructions like "stop", "slow down", "change lane left", each with its own ground-truth trajectory):
        1. The model predicts a trajectory for each instruction, as normal. 
        2. Then we flip the direction: take the model's own predicted trajectory, hide the camera image entirely, and show the model all K instructions from the group. 
        3. We score: "given only this trajectory, which of these K instructions is most likely to be the one that produced it?" - using the model's own language likelihoods. 
        4. The loss rewards the true instruction winning that comparison. 

    Intuition: if you rdriving genuinely follows your reasoning, then someone watching only your driving should be able to pick out which instruction you were given. If they can't, the reasoning wasn't really steering the wheel.

Yes, you've got it — with one clarification worth making precise: both directions are read off the same single measurement. We never run a second kind of pass that "predicts a trajectory from an instruction" inside the cycle loss (that's the job of the main forward loss). The cycle pass produces exactly one thing per group — the K×K matrix M, where every entry is "text scored behind a trajectory" — and the two questions are just two ways of slicing that same matrix:

- Read along a row (fix trajectory i, compare the K instructions): "conditioned on this trajectory, which instruction produced it?"
- Read along a column (fix instruction j, compare the K trajectories): "for this instruction, which trajectory did it produce?" — i.e., which trajectory made this text easiest to say.

And there's a nice symmetry in why the bug hit one direction and not the other. There are two possible kinds of baseline contamination:

- A per-instruction baseline p(j) — some texts are cheap for everyone. It's constant down a column, varies across a row. The row comparison is corrupted by it (that was the bug); the column comparison is automatically immune, because within one column all K entries share the same text and the baseline is identical everywhere you're comparing.
- A per-trajectory baseline q(i) — a trajectory whose encoding happens to make all text a bit easier or harder. It's constant along a row, varies down a column. Mirror image: the row comparison is automatically immune to it, and the column comparison is the one exposed.

The column-centering fix removes p(j) exactly, which repairs the row direction — and p(j) was the empirically huge one (several nats, since sentences differ wildly in length and commonness). To be fully honest about the residual: q(i) is not explicitly removed, so the column term is in principle exposed to it. It's expected to be small — the trajectories within a group are the same kind of object (same encoder, same token budget, same scene), unlike the instructions, which differ in wording and length — but it hasn't been measured the way p(j)'s dominance was. If the live runs show column-side accuracy lagging row-side, centering rows as well would be the one-line follow-up.

So the corrected picture: one matrix, two readouts, each readout naturally immune to one kind of baseline and vulnerable to the other; the fix removed the baseline that was actually dominating (the instruction prior), which is why the symmetric loss is now expected to train genuine trajectory↔instruction alignment in both directions.
