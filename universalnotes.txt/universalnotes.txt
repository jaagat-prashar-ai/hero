- The -0.4 value has two separate origins layered on top of each other — worth separating clearly:

1. The number itself is inherited, not derived. reasoning_threshold = -0.4 is copied verbatim from the vendored upstream NVlabs recipe (third_party/alpamayo-recipes/.../aggregated_reward_with_reasoning.py:109), which was built for a completely different grader — LingoJudge, a local text-similarity classifier outputting a raw quality score in [0,1], where reward = raw - 1.0 and -0.4 meant "pass if raw ≥ 0.6." Commit 77802f3 (2026-07-21, "add aggregated reward with LLM-judge reasoning component") explicitly ported this into the new gpt-4o-judge reward file with the note: "Mixing formula, thresholds, and return contract are preserved verbatim so the validated GRPO behavior carries over." So -0.4 wasn't chosen for the LLM judge — it was carried over unchanged when the judge was swapped in.

2. Mapping the new judge onto that inherited scale. The gpt-4o judge outputs an integer 0-10, not a [0,1] float, so normalize_score() (llm_judge.py:243) maps it: score/10 - 1.0. Under that mapping, -0.4 corresponds exactly to judge score > 6.

3. The only actual validation of "6" as a cut point: an offline calibration study — reasoning_matched_pairs.jsonl, 717 judged pairs across 120 scenes (commits fe87c81/63fa137, from the dpo_pairs/preference-pairs work) — where the judge scored "chosen" (real, good) vs. "corrupted" (perturbed, bad) reasoning traces. Result: chosen-trace median score 7, corrupted-trace median score 1. Since 6 sits just below the chosen median and well above the corrupted median, it was judged "a sensible acceptance bar" (comment in llm_judge.py:250).

The catch, already flagged in the code and still unresolved: that 717-pair calibration was run with the text-only judge prompt. The production path you're actually running (7bgtj3, scene-grounded — image + trajectory overlay) uses a different prompt variant, and the code comment itself (llm_judge.py:121-125) says the scene-grounded score distribution "may sit elsewhere" and to "watch the first canary run's histogram before trusting the threshold unchanged." Nobody has re-run the chosen-vs-corrupted calibration with the scene-grounded prompt — we only have the histogram I pulled from 7bgtj3 itself, which happens to be bimodal with nothing near the score-6 boundary, so at least the gate isn't splitting hairs on this particular run. But that's a property of this run's outputs, not a re-validation of 6 as the correct cut for the scene-grounded judge.

So: -0.4 is an inherited default, remapped by arithmetic, and loosely sanity-checked against a text-only calibration that predates the scene-grounded prompt actually in use. If you want a real answer on whether 6 is right for scene-grounded gpt-4o, the 717-pair chosen-vs-corrupted study would need to be redone with the scene-overlay prompt.

It doesn't get thrown away, and it doesn't just get one flat "you failed" value either. Two things can happen:

1. If the model didn't produce any usable reasoning text at all (empty output), it gets the worst possible score: flat -1.0.

2. If it did produce reasoning text but missed the bar — either the trajectory was too far off (ADE ≥ 3.0) or the reasoning score was ≤ -0.4 — it gets a graded failure score, somewhere between -1.0 and -0.5. Where exactly it lands depends on how close it came to passing on each of the two checks:

- How close was the trajectory error to the 3.0 cutoff? (barely over → more credit; way over → no credit)
- How close was the reasoning score to the -0.4 cutoff? (barely under → more credit; deeply negative → no credit)

Average those two "closeness" measures and that sets where in the -1.0-to-0.5 band it lands. Always strictly worse than any passing rollout (which starts around -0.2 and can go positive) — but not maximally punished if it was a near-miss.

Why bother grading a failure instead of just giving everyone -1? Because of how this training method (GRPO) uses reward: it doesn't train on the raw number, it compares each rollout to the average of the small group of attempts sampled for that same scene. If every single attempt in a group gets the exact same flat -1, there's zero difference between them — nothing to learn from, wasted judge calls. By grading "how close," even a group where everything technically failed still has some attempts that failed less badly than others, so there's still a gradient nudging the model toward the ones that came closer.

The five charts, in plain terms

Reward, mean — the single combined score (trajectory accuracy + comfort + reasoning bonus/penalty, all mixed together) averaged across each training step. Grey wiggly line = the real noisy value every step; blue line = a 15-step rolling average so you can see the trend through the noise. Here it just bounces around -0.2 with no upward or downward drift — the model isn't visibly "getting better" by this score yet.

Reasoning score — same idea, but isolating just the judge's reasoning component (scale -1 to 0). The dashed red line at -0.4 is the pass/fail cutoff. It sits around -0.25 on average, below the cutoff — which sounds bad, but isn't a contradiction with the 74% pass rate below: the passing rollouts score close to 0 (barely above the line), while the failing ones score very negative (-0.7 to -1.0), so the minority of failures drag the average down harder than the majority of near-perfect passes pull it up.

Trajectory L2 — how far the predicted path is from the real (ground-truth) path; smaller is better. Dashed red line at 3.0 is the cutoff. This is the one chart that shows a real, if modest, improvement — the smoothed trend drifts down from about 2.5 to about 2.2 over the run.

Gradient norm — how big each training update to the model's weights is, plotted on a log scale (because a few values spike into the 20s-30s). It starts small and calm, then gets bigger and spikier in the back half of the run. Nothing broke here, but it's a flag: if this run were extended or repeated, that rising instability is worth watching.

Judge score histogram — how many sampled rollouts got each possible score, 0 through 10. # Rollout / Training plots
    # For each prompt in a batch, the rollout worker (vLLM) samples n_generation=12 completions of that same prompt - that's the GRPO "group." 
    # Then those 12 completons get scored by the reward function (the LLM-judge, in this run) to get 12 reward values. 
    # "Train" = a separate step that happens after a group of rollouts exist. It takes the completed (prompt, completion, reward) tuples, computes each completion's advantage as reward minus the group's mean reward, and does the actual backward pass / optimizer step on the policy weights using that advantage. 
    # Rollout produces data: sample 12 completions per prompt, score them, push into a buffer. Runs on the vLLM rollout replica. 
    # Train consumes data: pull a batch of already-scored groups out of the buffer, compute GRPO loss, update weights. Runs on the policy replica.

├────────────────────────────────────────────────┼──────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤

└────────────────────────────────────────────────┴──────────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────┘
So it's assymetric: the language decoder is trained by two losses (langauge + contrastive), the trajectory decoder is trained by one (just its own regression losses) - that assymmetry is the entire point of the .detach() fix.
